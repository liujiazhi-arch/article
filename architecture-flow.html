article 项目当前架构流程图

更新于 2026-05-03。当前边界是“单篇 DOCX 论文格式审查、修复、复查、本地 API 与本地运维”，主链保持稳定，瘦身重点从“大入口文件”转向“薄壳、清晰模块、运行产物不进仓库”。

用户入口 本地壳/API 受保护主链 配置/运行态 已删除/产品边界外

1. 总流程：入口先变薄，主链不乱动

2. 当前三条可用链路

CLI 主链

  • 1用户执行 thesis-workbench audit/plan/apply/verify
  • 2thesis_workbench.py 解析 profile、scope、输出路径
  • 3workflow.py 编排审查、修复、复查
  • 4audit_thesis.py 与 fix_thesis.py 读写 OOXML
  • 5输出报告、新 DOCX 或 render-verify 证据

本地 API 单篇处理

  • 1article-api 等价于 article-local serve
  • 2app.py 只绑定路由和 HTTP 错误
  • 3请求模型、payload、上传任务适配由拆分模块承接
  • 4同步请求进 article_engine.service
  • 5异步请求进 jobs.py，纯 payload、执行、artifact 逻辑已拆到独立模块

本地运维链

  • 1article-local init 初始化 state/runtime/env
  • 2doctor 读取 app_ops.py 与 SQLite 状态
  • 3maintain 做状态库维护与 vacuum
  • 4backup/restore 打包和恢复本地状态
  • 5运行产物默认留在本地目录，不进入仓库维护面

3. 瘦身后的文件职责地图

scripts/thesis_workbench.py
推荐 CLI 入口。它是用户命令到核心 workflow 的桥，不再承接本地软件壳职责。
scripts/thesis_tool/workflow.py
稳定主链编排层。负责 scope 计划、apply、verify、normalize 与 render-verify 的组合逻辑。
scripts/audit_thesis.py
规则检查 runtime。读取 profile，扫描 DOCX，生成问题、报告与能力归类。
scripts/fix_thesis.py
自动修复核心。按 scope 写出新 DOCX，模板注入仍走 config/templates/<profile-id>/。
scripts/_thesis_utils.py
DOCX 结构底座。包含 DocumentModel、ParagraphNode、section/module 分类与共享 XML 工具。
scripts/article_engine/service.py
服务门面。把 CLI/API 统一成稳定 payload，再调用主链，避免 API 层直接理解太多论文规则。
scripts/article_api/local_app.py
本地壳入口。保留参数解析、命令分发、console script alias；preflight、normalize、render-verify、profiles 与运维命令从这里进入。
scripts/article_api/app.py
FastAPI 路由层。现在主要负责路由绑定、HTTP error、download response 与旧测试兼容 wrapper。
scripts/article_api/schemas.py
Pydantic 请求模型集中处，让 app.py 不再内嵌请求类。
scripts/article_api/request_payloads.py
同步请求和 job 请求参数构造，隔离“HTTP 请求字段”到“服务调用参数”的转换。
scripts/article_api/response_payloads.py
preflight、normalize、render-verify、服务版本等响应包装。
scripts/article_api/app_ops.py
health、version、ready、ops summary、storage/runtime payload 的集中构造。
scripts/article_api/app_uploads.py
上传视图、上传 cleanup、retention sweep 与 retention state helper。
scripts/article_api/upload_job_payloads.py
upload-backed verify/apply/normalize job 的参数适配。
scripts/article_api/job_queries.py
job 列表过滤逻辑，避免 app.py 内部继续堆筛选代码。
scripts/article_api/job_payloads.py
job 请求归一化、JobRecord、序列化、summary、runtime metadata 等纯结构逻辑。
scripts/article_api/job_execution.py
job runner 子进程、handler request、timeout/internal error、retryable 判断。
scripts/article_api/job_artifacts.py
artifact 快照、运行结束存在性冻结、cleanup candidate 路径判定。
scripts/article_api/jobs.py
异步任务生命周期门面，保留 create/retry/wait/cleanup/retention 等公开兼容入口。
scripts/article_api/storage.py
SQLite 状态层。保存 job、upload、cleanup、retention 等运行态数据。
config/
profile、能力矩阵、模板材料。新增 runtime 规则时必须同步测试和能力矩阵。

4. 当前瘦身判断

已经收紧的边界

  • 1产品边界从“什么都能处理”收敛到单篇 DOCX 论文链路。
  • 2app.py 已从肥路由开始拆成 schema、payload、ops、upload、query 模块。
  • 3jobs.py 第一轮已拆出 payload、execution、artifact 三个模块。
  • 4local_app.py 保持本地壳定位，doctor/maintain/backup/restore 走专门模块。
  • 5outputs/ 默认作为本地运行产物，不再作为仓库维护资产。

下一轮必须盯住

  • 1jobs.py 仍承担生命周期、recovery、retention、公开兼容 wrapper，后续可继续拆执行器门面。
  • 2API 层 wrapper 保留是为了兼容测试，下一步要判断哪些可以稳定迁移。
  • 3规则核心很大但属于主链，不能为了行数好看盲目拆。
  • 4运行环境要继续用安装、doctor、边界测试证明“一把通”。

5. 已删除或产品边界外

批量处理 article-local batch、/batch、/jobs/batch 不属于当前产品边界。
旧输出索引 仓库不再维护 outputs/ 下的 index、milestone、证据流水。
旧版本命名脚本 scripts/output_versioning.py 与对应测试已移出当前链路。
重复依赖入口 requirements.txt 已下线，依赖入口统一收敛到 pyproject.toml。
