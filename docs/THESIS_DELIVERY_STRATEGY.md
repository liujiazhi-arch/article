# 论文一键修复工具交付战略报告

> 日期：2026-06-16
> 目标：融合现有两版战略意见，形成面向学生交付体验的主战略。
> 依据：`docs/ONE_CLICK_THESIS_GAP_ASSESSMENT.md`、`docs/THESIS_PRODUCT_EXPERIENCE_STRATEGY.md`、`docs/THESIS_RESILIENT_DELIVERY_STRATEGY.md`、当前 CLI/API/前端契约与主链代码。

---

## 1. 总判断

这个项目下一阶段不该继续把主力压在“再多做几条规则”，而应该把能力组织成一个可信的论文交付系统。

学生真正关心的不是规则条数，而是这些问题：

1. 我上传论文后，工具到底帮我改了什么。
2. 哪些地方没改，为什么没改。
3. 哪些地方需要我确认。
4. 我现在该下载哪个文件。
5. 这份文件能不能直接交。
6. 如果还不能交，我下一步该做什么。
7. 如果我要找 AI 或老师继续处理，应该把什么材料发出去。

因此，产品主线应从“审查/修复命令”升级为“论文交付闭环”，但要比第一版战略更谨慎：

```text
上传原稿
  -> 自动结构修复
  -> 生成自动修复稿
  -> 说明已修改内容
  -> 说明未修改内容
  -> 识别失败/拦截/低置信时也给出诊断
  -> 需要时进入 PDF 复核
  -> 人工确认或生成候选稿
  -> 生成最终稿
  -> 打包学生报告和 AI 协作报告
```

这条链路的核心不是“每次都修成功”，而是“每次都诚实交付”。

---

## 2. 先校正事实，再谈战略

两版战略里有几处需要统一口径。

### 2.1 规则数量口径

公开 LNU runtime 当前能力矩阵记录为 75 条规则，不是 91 条。PDF 复核项另算，且不进入结构 runtime。

### 2.2 报告能力的真实状态

学生结论报告、AI 协作报告、PDF 复核报告并不是从零开始构想的空白页。项目里已经有初步 renderer 和文本骨架；真正缺口是它们没有稳定接入网页任务 artifact 和主交付路径。

### 2.3 PDF 能力的真实状态

PDF 复核不只是 2 条信号。代码里已经有空白页、渲染异常、孤立标点、公式编号跨页、标题页底孤行等启发式。问题不在“有没有”，而在“哪些足够可信、怎么给学生看、怎么进入闭环”。

### 2.4 失败与不确定不是边角料

原来的交付思路偏顺利路径。另一版战略提醒得更对：脏文档、识别错、修复错、复核不准，都必须被当成一等产品情况，而不是只返回错误码。

## 3. 战略主轴

建议把战略拆成两根轴。

### 3.1 轴一：把成功结果交付漂亮

这就是原战略的主轴：

- 自动修复稿清楚可下载。
- 已改内容看得懂。
- 未改内容能解释。
- PDF 复核能回到 DOCX。
- 最终稿能生成。
- ZIP 能交付。

### 3.2 轴二：把每一种结果交付诚实

这是另一版战略补出来的下限，也是更关键的产品承诺：

- 修不成也要给诊断。
- 被 guard 拦截也要说明风险。
- 改了但不确定也要标明。
- 低置信发现不能伪装成确定结论。
- 失败态不能只有红叉，必须有下一步。

**结论：先诚实，再漂亮。**

## 4. 产品目标

下一阶段建议把产品目标定义为：

> 学生上传一篇论文后，工具能自动修复确定性格式问题，生成可下载修复稿，并清楚说明已改内容、未改内容、需要确认的内容；当识别失败、修复被拦截或结果低置信时，仍然输出学生看得懂的诊断；如果存在 PDF 版式问题，能引导学生确认并生成候选稿或最终交付包，同时提供学生可读报告和 AI 协作报告。

这个目标拆成五个承诺。

### 4.1 能改

学生上传 DOCX 后，工具应自动完成确定性结构修复：

- 页边距、页码、字体、字号、行距、首行缩进、对齐。
- 标题格式、编号间距、段前段后、章前分页。
- 摘要、关键词、目录、致谢等前后置模块。
- 图题、表题、三线表、图片居中、图表块保护。
- 参考文献缩进、编号、类型标识、标点、引用上标。
- 中英文混排空格、数字单位间距、公式说明格式。

### 4.2 能解释

每次修复后必须能回答：

- 改了哪些范围。
- 改了哪些规则。
- 改了多少类问题。
- 典型位置在哪里。
- 为什么这些问题可以自动改。
- 修复后还剩哪些提示。

解释应分层：

- 页面上显示摘要和下一步。
- 学生报告显示具体问题和建议。
- 技术报告保留规则 ID、scope、证据、调试信息。
- AI 报告保留结构化上下文和安全边界。

### 4.3 能说明没改

未修复项必须成为一等产物，而不是藏在失败规则里。

建议分五类：

| 类别 | 含义 | 示例 | 产品动作 |
|------|------|------|----------|
| 需要确认 | 程序能定位，但需要学生判断 | 末章是否叫结论 | 显示确认卡片 |
| 需要人工处理 | 程序不应改内容语义 | 参考文献大小写一致性 | 给出人工建议 |
| 需要 PDF 复核 | DOCX 结构看不到真实分页 | 目录页码、孤立标点 | 引导上传 PDF |
| 暂不支持 | 当前能力未覆盖 | 特殊脚注或复杂版式 | 写入待办和报告 |
| 可信度风险 | 引擎可能识别错、修错或复核不准 | 表格被误判为标题、低置信 finding、guard 拦截项 | 明确标注不确定，给核对入口和出路 |

### 4.4 能诚实

这是比“能改”更重要的承诺。

每一种异常都要有明确落点：

- 失败：修不成也给诊断。
- 拦截：为什么没敢改，风险是什么。
- 低置信：改了，但建议复核。
- 不确定：明确写不确定，不假装确定。

### 4.5 能交付

最终交付不应只是一个 DOCX，而应是一组清楚命名的结果：

```text
原稿.docx
自动修复稿.docx
候选修复稿.docx
最终稿.docx
学生结论报告.md
AI协作报告.md
技术明细报告.md
PDF复核报告.md
失败诊断报告.md
```

第一阶段不一定全部生成，但产品心智必须向这个方向统一。

## 5. 当前项目位置

### 5.1 已经比较强的部分

当前主链是：

```text
scripts/thesis_workbench.py
  -> scripts/thesis_tool/workflow.py
    -> scripts/audit_thesis.py / scripts/fix_thesis.py
      -> scripts/_thesis_utils.py
```

这条链路的优势很清楚：

- OOXML 结构层规则已经覆盖大量刚性格式问题。
- scope 化修复已经存在，能按摘要、目录、标题、正文、图表、参考文献等范围处理。
- 自动修复后可以复查。
- 本地网页已经有上传、任务、历史、下载、PDF 复核的基础。
- PDF 复核已经具备页图、bbox、缺图降级和截图注册能力。
- CLI 侧已经有学生结论报告、AI 上下文报告和 PDF 复核报告的雏形。
- 失败分类、guard、post-verify notice 和 confidence 字段都已经存在。

这说明项目不是“还没成型”，而是“能力分散在引擎、CLI、API、前端之间，尚未形成统一交付”。

### 5.2 当前体验断点

从学生视角看，现状断点主要有六类。

第一，修复结果不够解释化。

工具可以生成修复稿，但学生不知道具体改了哪些规则、哪些段落、哪些问题仍然存在。

第二，未修复项不够清楚。

一些问题程序能检测但不应该自动改，例如参考文献题名大小写一致性、末章是否应命名为结论、PDF 中的孤立标点、目录真实页码。

第三，失败态没有产品化。

修不成、被拦截、解析失败时，今天往往只剩一个错误态，而不是一份学生可读诊断。

第四，PDF 复核是只读终点。

PDF 复核可以标出渲染问题，但用户确认之后没有一条明确路径回到 DOCX 生成最终稿。

第五，文件阶段感不强。

现在用户能看到输入文件、输出文件、报告文件，但产品没有明确告诉用户哪个是建议提交的版本。

第六，报告没有形成分层交付。

学生需要短、清楚、可行动的报告。AI 协作需要结构化、可复制、带边界说明的上下文。开发者或高级用户需要技术明细。三者不应混在一起。

## 6. 产品形态

### 6.1 首页不是“上传文件”而是“论文交付工作台”

学生进入页面后看到的主流程应该是：

```text
1 上传论文
2 自动修复
3 查看改了什么
4 处理剩余问题
5 下载可交付文件
```

每一步都应有明确状态：

- 未开始
- 正在处理
- 已完成
- 需要你确认
- 建议复核 PDF
- 可以下载
- 处理失败但已生成诊断
- 有低置信改动需要复核

UI 文案要面向学生，不展示 `job_id`、`queued`、`running`、`bbox`、`rule_id` 等内部词。

### 6.2 修复完成页要成为核心页面

当前最重要的页面不是上传页，而是修复完成页。它应该回答四件事：

1. 已帮你完成哪些修改。
2. 还有哪些地方需要你看。
3. 是否建议上传 PDF 复核。
4. 现在可以下载哪些文件。

建议页面结构：

```text
顶部结论
  例如：已生成自动修复稿 还有 3 类问题需要确认

下载区
  自动修复稿
  学生结论报告
  AI协作报告
  失败诊断报告（如有）

已修复内容
  按范围展示：摘要 标题 正文 图表 参考文献

需要确认
  每类问题一张卡片
  显示位置 示例 建议 下一步

低置信改动
  标出“我们改了，但建议你复核”

PDF复核
  如果有目录页码或版式风险
  提示导出 PDF 后上传复核

下一步
  下载自动修复稿
  上传 PDF 复核
  生成最终交付包
```

### 6.3 报告分四种

#### 学生结论报告

目标：让学生知道怎么处理论文。

风格：短句、中文、少术语、按行动组织。

#### AI 协作报告

目标：学生可以复制给其他 AI 或老师，让对方继续处理工具不该自动改的问题。

风格：结构化、带边界、防注入、保留原文片段。

#### 技术明细报告

目标：调试、复查、开发、评估。

风格：允许规则 ID、scope、evidence、action、source。

#### 失败诊断报告

目标：修不成、拦截、解析失败时，仍然给学生下一步。

风格：回答卡在哪、为什么卡、怎么办、发给谁看。

## 7. PDF 复核闭环设计

### 7.1 PDF 复核的产品定位

PDF 复核不是另一个自动修复器，而是最终提交前的版式证据检查。

它解决 DOCX 结构层看不到的问题：

- 目录页码是否和渲染页一致。
- PDF 里是否出现孤立标点。
- 标题是否单独留在页底。
- 公式编号是否跨页。
- 是否出现空白页或渲染异常页。
- 图表块是否疑似被拆开。

这些问题必须标记为“疑似”或“需要确认”，不能包装成确定错误。

### 7.2 PDF 台不应直接改 PDF

PDF 是终态证据，不是编辑对象。正确路径是：

```text
PDF 发现问题
  -> 学生确认
  -> 映射到 DOCX 修复动作或人工建议
  -> 生成候选稿
  -> 学生重新导出 PDF
  -> 再次复核
```

因此，PDF 台应该提供三类动作：

| 动作 | 含义 |
|------|------|
| 确认是问题 | 进入修复或候选稿流程 |
| 不是问题 | 从待处理清单移除，但记录在报告 |
| 我自己处理 | 写入最终报告，不自动改 |

第一版不建议支持自由文本自动回填。自由文本可以先作为备注进入报告，后续再设计映射。

### 7.3 候选稿机制

对于 PDF 版式问题，建议生成“候选稿”而不是直接覆盖“最终稿”。

候选稿适合处理：

- 图表挤页。
- 标题页底孤行。
- 公式编号跨页。
- 目录需要刷新后的页码复核。

候选稿必须配合二次 PDF 复核。只有二次复核通过后，才升级为最终稿。

## 8. 文件生命周期战略

当前产品最大的不安全感来自“我不知道哪个文件该交”。所以文件生命周期必须明确。

建议定义以下阶段：

| 阶段 | 文件 | 含义 |
|------|------|------|
| 原稿 | `原稿.docx` | 学生上传的文件，不修改 |
| 自动修复稿 | `自动修复稿.docx` | 确定性规则已处理 |
| PDF 复核证据 | `复核页图/复核PDF` | 用于判断真实版式 |
| 候选稿 | `候选修复稿.docx` | 根据确认项尝试调整 |
| 最终稿 | `最终稿.docx` | 当前推荐提交版本 |
| 报告包 | 多份报告 | 说明处理过程和剩余问题 |
| 失败诊断包 | 多份诊断 | 说明为什么没修成、下一步怎么办 |

文件命名建议使用学生能理解的中文，不直接暴露 operation 名称：

- `论文_自动修复稿.docx`
- `论文_候选修复稿.docx`
- `论文_最终稿.docx`
- `论文_学生结论报告.md`
- `论文_AI协作报告.md`
- `论文_技术明细报告.md`
- `论文_失败诊断报告.md`

后续如果打包 ZIP，ZIP 名称可以是：

```text
论文格式处理结果_2026-06-16.zip
```

ZIP 内建议放一个 `请先看我.md`，告诉学生：

- 推荐先打开哪个文件。
- 哪个文件是最终稿。
- 哪些问题还需要确认。
- 如果找 AI 或老师帮忙，该发哪份报告。
- 如果本次失败了，先看哪份诊断。

## 9. 战略优先级

### P0：交付报告主线 + 失败诊断接线

这是最应该先做的方向。

目标：

- apply 任务完成后，不只生成 `job_report.md`。
- 生成学生结论报告。
- 生成 AI 协作报告。
- 生成技术明细报告。
- 生成失败诊断报告。
- 前端修复完成页展示报告摘要。
- 下载区明确展示每份文件的用途。

原因：

- 对用户价值最高。
- 实现成本相对低。
- 现有 `conclusion_report.py`、`errors.py`、`build_failure_summary` 和 evidence groups 已有基础。
- 能立刻把产品从“工具”变成“交付系统”。

验收标准：

- 上传一篇有格式问题的 DOCX。
- 自动修复完成。
- 页面显示已修复和待确认摘要。
- 下载学生报告。
- 报告中能看到问题类别、位置、原文示例、建议。
- 下载 AI 报告。
- AI 报告结构化列出待确认问题，并声明边界。
- 上传一篇损坏或极脏的 DOCX。
- 系统不崩。
- 能下载失败诊断报告，说明卡在哪、为什么、下一步怎么办。
- guard 拦截样本也能给出解释和出路。

### P1：任务结果页重构

目标：

- 修复完成页成为结果中心。
- 历史任务可重开同样的结果中心。
- 每个 artifact 都有学生可读用途说明。
- 未修复项不再只是失败规则，而是待确认清单。
- 失败、拦截、低置信状态也能在页面上解释清楚。

原因：

- 体验闭环需要界面承载。
- 只下载文件不够，学生需要现场判断下一步。

验收标准：

- 页面不展示内部术语。
- 能看到“已帮你改”“还需要你确认”“建议复核 PDF”“下载文件”。
- 历史任务恢复后仍能看到相同摘要。
- 失败任务重开时，能看到为什么失败和下一步。

### P2：PDF 复核确认流 + 置信度分层

目标：

- PDF 复核问题进入确认清单。
- 用户可以确认、忽略、标记自己处理。
- 确认结果写入报告。
- 可映射项生成候选稿。
- 低置信发现折叠展示，不伪装成确定结论。

原因：

- 这是从“只读 PDF 台”走向闭环的关键。
- 但它比报告主线复杂，应该排在报告之后。

验收标准：

- 上传 DOCX 和 PDF。
- PDF 台列出问题。
- 用户逐项确认。
- 确认结果能保存。
- 报告说明每项处理结果。
- 可支持的项能生成候选稿。

### P3：最终交付包

目标：

- 一键下载完整交付 ZIP。
- 包含最终稿、报告、原稿索引和说明。
- 清楚标注推荐提交文件。
- 包含失败诊断包的入口。

原因：

- 这是学生最容易理解的交付形式。
- 也方便以后做桌面版、Windows 本地包和反馈包。

验收标准：

- ZIP 中没有运行状态、缓存、日志、上传路径等隐私或内部信息。
- ZIP 内文件命名清楚。
- `请先看我.md` 能解释所有文件用途。

### P4：PDF 可信复核项产品化

目标：

- 从已有启发式中筛选可信项。
- 统一规则 ID、学生文案、AI 文案、报告文案。
- 增加测试样本。

优先项：

1. 目录页码不一致。
2. 孤立标点。
3. 空白页或渲染异常。
4. 公式编号跨页。
5. 标题页底孤行。
6. 图表/题注疑似跨页。

注意：

- 不要追求字符级高亮作为近期目标。
- 不要为了“看起来强”展示低置信噪声。
- 每个 PDF finding 都要能解释为什么只是疑似。

---

## 10. 不建议优先做的方向

### 10.1 不建议继续大规模加结构规则

结构规则仍然可以补，但不是主线。

可以顺手补的：

- FN01 脚注字号自动修复。
- 少量证据更清晰的参考文献格式项。

不建议强行自动化的：

- 参考文献题名大小写语义判断。
- 末章标题是否应该叫结论。
- 目录真实页码。
- PDF 孤立标点自动回写。

这些问题应该进入确认流和报告，而不是静默自动改。

### 10.2 不建议做直接 PDF 编辑

PDF 是终态证据，不是修复源。应该回到 DOCX 处理。

### 10.3 不建议第一版做自由文本回填

“用户说怎么改，系统自动改”听起来完整，但第一版风险太高。

第一版应该做结构化确认和有限动作。自由文本备注先进入报告，不自动执行。

### 10.4 不建议把 AI 放进确定性修复主链

项目优势是确定性、可复现、本地、可解释。AI 可以用于协作报告、用户另行处理、语义建议，但不应替代格式引擎做静默修改。

## 11. 架构演进建议

### 11.1 P0 不提前抽象 DeliveryResult

`DeliveryResult` 是中后期需要的统一结果模型，但不应该作为 P0 的前置条件。

当前代码里已经有一条更轻的路径：`scripts/thesis_tool/workflow.py` 的 `build_audit_human_reports()` 只需要文件路径，就能重跑审查并生成学生结论报告、AI 协作报告和技术明细报告。P0 应优先复用这条自包含路径，而不是从持久化 job payload 里重建 findings。

原因：

- apply 持久化 summary 已经被裁剪，不保留逐条 evidence。
- 从 payload 重建报告会引入新的数据模型和解析逻辑。
- 对修复稿重跑 audit 是确定性、幂等、成本可控的。
- 当前阶段目标是接通交付，而不是提前设计跨阶段对象。

因此，P0 只做：

```text
修复稿路径
  -> build_audit_human_reports()
  -> 注册 student_report / ai_report / technical_report artifact
```

`DeliveryResult` 推迟到 P2/P3，当 PDF 确认状态、候选稿、最终稿、交付包确实需要跨阶段聚合时再引入。

### 11.2 后续再把结果模型提升为核心对象

当进入 PDF 确认、候选稿和最终交付包阶段后，再统一一个交付结果模型，避免每个 job 自己拼跨阶段状态。

概念结构：

```text
DeliveryResult
  document
  outcome            # success | partial | guard_blocked | failed
  stages             # original / auto_fixed / candidate / final
  fixed_items
  low_confidence_fixes
  unresolved_items
  guard_findings
  review_items
  diagnosis
  artifacts
  reports
  next_steps
```

其中 unresolved item 建议包含：

```text
id
source_rule_id
scope_id
title_for_student
technical_title
status
reason_not_fixed
location
examples
suggested_action
can_generate_candidate
requires_pdf
requires_human_confirmation
confidence
why_uncertain
student_explanation
escapes
```

这样前端、报告、ZIP、历史记录都能从同一个模型读数据。

### 11.3 报告生成器从 CLI 能力升级为服务能力

当前 `build_audit_human_reports()` 更像 CLI 专用入口。建议 P0 先把它包装成服务层可复用能力：

```text
build_delivery_reports(file_path)
  -> student_report
  -> ai_context_report
  -> technical_report
  -> failure_report
```

成功路径按磁盘上的修复稿重跑审查并生成报告；失败路径不跑 audit，只用错误摘要生成失败诊断报告。然后由 `article_api/job_artifacts.py` 统一注册 artifact。

### 11.4 artifact 应支持多报告角色

现在 `report` 只有一个角色。建议扩展为：

```text
student_report
ai_report
technical_report
render_report
failure_report
delivery_package
```

前端下载区根据 role 展示学生文案：

- 学生结论报告：适合自己看。
- AI 协作报告：适合发给 AI 或老师继续处理。
- 技术明细报告：适合排查问题。
- 失败诊断报告：适合知道卡在哪、为什么、下一步。
- 完整结果包：包含所有文件。

### 11.5 历史任务要保存交付语义

历史记录不应只是 job list。它应该能恢复：

- 当时生成了哪个修复稿。
- 哪些问题未处理。
- 是否做过 PDF 复核。
- 是否生成过候选稿。
- 当前推荐下载哪个文件。
- 是否失败、拦截或低置信。

这要求持久化 summary 时保留 delivery result 的关键字段，而不只保留任务运行状态。

## 12. 前端体验方向

### 12.1 页面文案原则

学生界面应避免：

- `job_id`
- `queued`
- `running`
- `failed`
- `rule_id`
- `bbox`
- `artifact`
- `render-verify`
- `/jobs/{id}`

对应替换：

| 内部词 | 学生文案 |
|--------|----------|
| apply | 自动修复 |
| verify | 复查结果 |
| render-verify | PDF 版式复核 |
| artifact | 下载文件 |
| failed rules | 需要处理的问题 |
| manual_review | 需要你确认 |
| unsupported | 暂时不能自动处理 |
| bbox | 问题位置 |

### 12.2 页面信息层级

推荐每个结果页只回答当前最关键的三个问题：

1. 现在处于哪一步。
2. 结果是什么。
3. 下一步做什么。

详细内容放进展开区和报告下载，不要把所有技术细节堆在页面上。

### 12.3 PDF 台体验

PDF 台应该像批改清单：

- 左侧问题列表。
- 中间页图。
- 右侧确认动作。
- 底部显示“已确认 X 个，还剩 Y 个”。

每个问题都要有学生文案：

```text
第 12 页
疑似有单独标点
建议回到 Word/WPS 调整这一段后重新导出 PDF

[这是问题] [不是问题] [我自己处理]
```

不要显示 `render.isolated_punctuation` 或 bbox 数字。

## 13. 测试和验收策略

### 13.1 产品级测试样本

建议建立 5 类公开脱敏样本：

1. 结构格式混乱样本。
2. 有人工确认项样本。
3. 有 PDF 复核项样本。
4. 损坏或极脏 docx 样本。
5. 完整闭环样本。

每类样本都应验证：

- 修复稿生成。
- 学生报告生成。
- AI 报告生成。
- 失败诊断生成。
- 未修复项分类正确。
- 下载文件命名正确。
- 前端不泄漏内部术语。

### 13.2 报告质量测试

报告不能只测文件存在，还要测内容：

- 学生报告包含“已帮你修改”“需要你确认”“建议复核 PDF”。
- AI 报告包含安全边界。
- 技术报告包含 rule、scope、evidence。
- 失败诊断报告包含卡点、原因、下一步。
- 学生报告不出现内部 endpoint、bbox、JSON、raw rule dump。
- AI 报告中论文原文放在 fenced block，避免提示注入。

## 14. 建议实施路线

### 第一阶段：报告交付化

范围：

- apply job 生成学生结论报告。
- apply job 生成 AI 协作报告。
- apply job 生成技术明细报告。
- 失败/拦截/错误路径生成失败诊断报告。
- 前端下载区显示报告用途。
- 结果页显示已修复/待确认/低置信/失败摘要。

不做：

- PDF 回填。
- 最终稿生成。
- 新增复杂 PDF 规则。

预期收益：

- 学生能看懂结果。
- 工具显得完整可信。
- 为后续闭环积累统一数据模型。

### 第二阶段：未修复项工作台

范围：

- 把 manual review、unsupported、render required、low confidence、guard findings 统一成待处理清单。
- 每项有状态：待确认、已忽略、自己处理、已生成候选稿。
- 状态进入报告和历史任务。

不做：

- 自由文本自动修改。

### 第三阶段：PDF 确认和候选稿

范围：

- PDF finding 可确认。
- 可映射项生成候选稿。
- 候选稿必须再次 PDF 复核。
- 报告记录每项确认结果。

### 第四阶段：最终交付包

范围：

- 生成最终稿。
- 生成完整 ZIP。
- ZIP 中有说明文件。
- 历史任务可重新下载交付包。

### 第五阶段：PDF 复核项精炼扩展

范围：

- 产品化 4-6 个可信 PDF 项。
- 给每个项补报告文案、前端文案、测试样本。

## 15. 最终建议

项目未来应该围绕“交付闭环”而不是“规则数量”前进，但闭环必须建立在“诚实交付”之上。

最重要的第一步是：把一次自动修复任务的结果变成学生能理解的交付结果。也就是让学生上传文件后，马上得到：

- 一份自动修复稿。
- 一份说明改了什么的学生报告。
- 一份说明没改什么和为什么没改的清单。
- 一份能交给 AI 继续处理的结构化报告。
- 一份失败时也能看懂的诊断报告。
- 一个清楚的下一步建议。

当这个基础体验稳定后，再做 PDF 确认、候选稿、最终稿和完整 ZIP。这样路线最稳，也最符合当前项目已有能力。

短期口号可以定为：

> 改得了就改好，改不了就说清，绝不假装确定。

长期产品形态则是：

> 本地可信、且在不确定时依然诚实的论文格式交付工作台。
