# Frontend Workbench And PDF Review Plan

> Superseded: This visual/product plan is retained as context. Implementation must follow `docs/superpowers/plans/2026-06-16-frontend-workbench-contract-implementation-plan.md` and `docs/FRONTEND_BACKEND_CONTRACT.md` first.

Date: 2026-06-16

## Purpose

把当前前端从展示型原型升级为学生可真实使用的论文修正工作台。

本计划聚焦三件事：

- 后端功能完成后，前端功能如何对应变化
- PDF 复核如何做到真实问题预览
- 字体、文案、排版、主题资产如何符合本项目已确认规范

## Source Rules

实施前必须遵守：

- `AGENTS.md`
- `docs/FRONTEND_UI_STYLE_GUIDE.md`
- `frontend-architecture-rules`
- `impeccable-image-theme`

本计划不替代上述规范。若出现冲突，以上述规范和用户最新反馈为准。

## Product Direction

前端不再表达“系统做了什么技术动作”，而是表达“学生现在该做什么”。

学生主流程应变为：

```text
上传论文
  -> 生成修正方案
  -> 选择处理范围
  -> 生成修正副本
  -> 上传或导入 PDF
  -> 查看问题预览
  -> 下载结果
```

所有主界面文案必须面向学生，避免开发态术语。

避免出现在学生主界面：

- `/jobs/{id}`
- `queued`
- `running`
- `failed`
- `succeeded`
- `bbox`
- `JSON`
- `report artifact`
- `rule_id`
- `任务轮询`

推荐替换为：

- `处理进度`
- `下一步提示`
- `需要你确认`
- `问题位置`
- `报告文件`
- `修正副本`
- `PDF 复核`

## Target Screens

第一版保留现有主题系统，但重新整理功能信息架构。

### 1. Cover

目标：

- 进入工具
- 查看历史
- 选择主题

改动：

- `辽宁大学` 固定为一行
- 主标题按主题区分字体气质、色温、阴影和光带
- 主按钮和次按钮都跟随当前主题 token
- 不允许四个主题共用完全一样的按钮颜色

验收：

- 四个主题标题一眼能区分
- `辽宁大学` 不断行
- `进入工具` 和 `查看历史` 都与当前主题协调

### 2. Upload And Plan Workbench

目标：

- 上传 `.docx`
- 生成修正方案
- 选择处理范围

推荐布局：

```text
左侧    上传论文
中间    修正方案和范围选择
底部    流程步骤
右侧    下一步提示
```

学生可见文案示例：

```text
上传论文
放入 docx 文件

生成修正方案
先查看问题 再选择范围

选择处理范围
摘要 目录 正文 参考文献

生成修正副本
原文件不会覆盖
```

改动：

- 移除突兀白底上传卡
- 使用深色半透明玻璃底
- 重要说明字号不低于 15px
- 流程步骤字号 15px 起
- 卡片标题 16-17px
- 信息不要堆在上半部分

验收：

- 页面下半部分有流程和状态承载
- 上传区不再像独立白纸贴片
- 用户能在 5 秒内看出第一步是上传论文

### 3. Progress And Scope Review

目标：

- 展示系统处理进度
- 展示哪些范围可修
- 展示哪些位置需要学生确认

推荐状态分组：

```text
当前进度
下一步
需要确认
```

流程卡示例：

```text
已读取论文结构
已生成修正方案
正在处理正文格式
等待 PDF 复核
```

改动：

- 右侧栏不显示轮询、接口、英文状态
- 不把状态全部挤在上半部分
- 纵向分布状态卡，填满可用高度
- 空白服务阅读节奏，不留无意义大空区

验收：

- 无开发态状态词
- 无大段小字堆叠
- 用户能理解当前卡住在哪里

### 4. PDF Review Evidence Viewer

目标：

把 PDF 复核从装饰模块改成真实证据查看器。

推荐布局：

```text
左侧    问题列表
中间    PDF 页面截图和高亮框
右侧    问题说明和处理建议
底部    上一处 下一处 缩放 隐藏高亮
```

左侧问题列表示例：

```text
第 12 页
标点单独成行

第 18 页
标题靠近页底

第 23 页
目录页码疑似错位
```

右侧说明示例：

```text
问题位置
第 12 页底部

可能影响
页面观感不整齐

建议处理
回到 Word 调整段落
重新导出 PDF 后复查
```

第一版真实能力：

- 显示真实 PDF 页面截图
- 点击问题切换到对应页
- 使用后端 `bbox` 或 `region` 映射高亮框
- 支持上一处和下一处
- 支持放大缩小
- 支持显示或隐藏高亮

后端字段建议：

```json
{
  "id": "issue-12-1",
  "student_title": "标点单独成行",
  "page": 12,
  "bbox": {
    "x": 0.12,
    "y": 0.74,
    "w": 0.72,
    "h": 0.06
  },
  "screenshot_url": "/render-evidence/screenshot/abc123",
  "student_message": "这一页底部有单独标点",
  "next_action": "调整 Word 段落后重新导出 PDF"
}
```

前端映射规则：

- `bbox.x` 和 `bbox.y` 使用页面图片宽高的百分比定位
- `bbox.w` 和 `bbox.h` 使用页面图片宽高的百分比绘制
- 缩放时高亮框跟随页面容器缩放
- 无 `bbox` 时退化为整页提示，不伪造精确框

第二阶段精确能力：

- 增加文字级坐标
- 支持高亮某一行、某个标点或某个文字片段

后端可选实现：

- `pdftotext -bbox-layout`
- `pdfplumber`
- `PyMuPDF`

第二阶段字段建议：

```json
{
  "text_spans": [
    {
      "text": "。",
      "page": 12,
      "bbox": {
        "x": 0.63,
        "y": 0.82,
        "w": 0.02,
        "h": 0.018
      }
    }
  ]
}
```

验收：

- PDF 复核区不再是静态装饰
- 问题列表与页面预览联动
- 高亮框位置稳定
- 学生能看懂问题和下一步
- 无 `bbox`、`render`、`artifact` 等技术词出现在主界面

### 5. History

目标：

- 展示历史处理记录
- 让学生找到可下载副本和报告

改动：

- 任务标题和说明字号增大
- 历史项不再像压缩日志
- 背景图不能干扰文字
- 历史页背景板跟随当前主题，不继承错误主题资产

历史项示例：

```text
本科论文终稿
今天 06:18
已生成修正副本

PDF 复核
今天 06:03
发现 3 处需要确认
```

验收：

- 字体不小于当前规范
- 历史项有清晰层级
- 用户能直接找到下载和复核入口

### 6. Result

目标：

- 下载修正副本
- 查看审查报告
- 进入 PDF 复核
- 提示下一步

推荐卡片：

```text
修正后论文
下载 docx 副本

审查报告
查看问题摘要

PDF 复核
检查导出效果

下一步
保存副本后提交
```

改动：

- 不使用与主题冲突的浅色大纸板
- 下载入口、报告、PDF 复核和下一步分块展示
- 结果页背景板跟随当前主题
- 重要按钮颜色跟随主题 token

验收：

- 结果页不拥挤
- 下载入口足够明显
- 雨后主题不出现暖色错配资产

## Typography Rules For This Plan

实施时采用以下字号底线：

- 页面主标题：28-40px
- 面板标题：24px 起
- 卡片标题：16-17px
- 重要正文说明：15-16px
- 步骤块文字：15px 起
- 标签和元信息：11-12px 仅用于不影响理解的辅助信息

排版要求：

- 一行中文尽量不出现逗号、句号、冒号、顿号
- 长句拆成短行、卡片、标签或标题说明结构
- 玻璃态面板可以透明，正文不能透明到难读
- 背景复杂时内容区域必须有深色内衬或遮罩
- 不允许重要信息压成小字说明

## Theme Asset Rules

每个主题至少检查：

```text
--hero-image
--asset-board
--asset-workflow-board
--asset-pdf-board
--asset-result-board
```

第一版重点：

- 雨后主题补齐或替换 workflow board
- 雨后主题补齐或替换 pdf board
- 雨后主题补齐或替换 result board
- 四个主题按钮 token 匹配
- 四个主题标题 token 匹配

如果现有资产不足，优先使用 `impeccable-image-theme` 工作流：

```text
参考图或生成图
  -> 提取视觉方向
  -> 生成或补齐配套图
  -> 定主题 token
  -> 定配色 字体 材质
  -> 生成匹配 UI 组件
  -> 浏览器截图校验
```

生图不应零散生成。至少按同一主题的光线、材质、色温和负空间生成成套图。

## Implementation Order

### Step 1. Inventory

检查当前前端文件、主题 token、静态资源、预览入口和后端 payload。

输出：

- 目标文件清单
- 当前主题资产清单
- PDF 复核 payload 可用字段清单

### Step 2. Copy And Typography Pass

先改学生可见文案和字号。

目标：

- 移除开发态术语
- 拆短长句
- 提升正文和步骤字号
- 修正标点堆叠问题

### Step 3. Layout Pass

重排工作台、状态栏、历史页和结果页。

目标：

- 信息不再集中在上半部分
- 下半部分承载流程、状态或下一步
- 卡片密度更舒展
- 玻璃底更稳定

### Step 4. PDF Review Viewer

实现真实证据查看器。

第一版可以先用 mock 数据或后端现有 payload 结构对齐。

必须支持：

- 问题列表
- 页面截图
- 区域高亮
- 上一处和下一处
- 缩放
- 隐藏高亮
- 无精确区域时的整页提示

### Step 5. Theme Token And Asset Pass

修复四个主题的标题、按钮、背景板和面板色彩。

重点检查：

- 雨后主题
- 雪景主题
- 按钮颜色
- 标题差异化
- 结果页背景板

### Step 6. Browser Verification

使用 Browser 或 Playwright 检查：

- 4 个主题
- Cover
- Workbench
- PDF Review
- History
- Result
- 桌面视口
- 窄屏视口
- 控制台错误

## Out Of Scope For First Version

第一版暂不要求：

- 精确到单个字符的 PDF 高亮
- 在线编辑 Word 内容
- 自动覆盖原文件
- 多人协作
- 云端账号系统
- 复杂动画

这些能力可以在 PDF 页面预览稳定后再扩展。
