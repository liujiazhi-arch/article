# 一键修复论文工具 · 能力差距评估

> 评估日期：2026-06-16
> 评估方式：只读代码 + 真实 TestClient 端到端跑通验证，未改动任何代码。
> 评估目标：判断当前工具距离「论文丢进去一键修，改不了的交 PDF 台人工确认，确认后回填生成最终稿，全程文件清晰、报告人/AI 双可读」还差什么。

---

## 一句话结论

**修复引擎已经够强，差距不在「修不修得了」，而在「交付闭环」。**

按性价比，缺的三块依次是：详细报告（给人+给AI 两份）、PDF 确认→回填→定稿闭环、PDF 渲染规则扩展。

## 1. 一键自动修复：火候够 ✅

OOXML 结构层检测+修复是最扎实的部分，确定性强、可重复：

- 页边距、字体字号行距、首行缩进、两端对齐
- 标题各级格式与编号、段前段后间距、章前分页
- 图表题注、三线表边框、图片居中
- 参考文献悬挂缩进/编号/类型标识、引用上标
- 摘要/关键词/目录/致谢格式、中英文混排空格紧凑化

**只有 5 条是「测得出、改不了」，且都有道理：**

| 规则 | 原因 |
|------|------|
| FN01 脚注字号 | 当前未接修复 |
| LNU_REF06 题名大小写一致性 | 涉及语义判断 |
| LNU_CONC01 末章是否叫「结论」 | 纯人工确认 |
| LNU_TOC04 目录页码与渲染页一致 | 依赖 PDF 渲染，结构层看不到 |
| PDF_PUNCT01 PDF 孤立标点 | 依赖 PDF 渲染 |

**判断：自动修复侧不需要大扩展，边际收益低。**

---

## 2. PDF 复核台：确实差点火候，且是真·技术难点 ⚠️

现在只有 **2 条** 渲染规则。这块弱，但要诚实区分它和结构层是两种问题：

- **依赖外部渲染**：docx→PDF 靠 Word/WPS/LibreOffice，不同引擎分页、字体回退结果不同，判断天生不稳（fidelity 问题）。
- **图像启发式，非精确判定**：孤立标点、空白页、标题孤行是版式特征，属「疑似」而非「确定」，所以注定是 `Semi`（程序定位 + 人工确认）——这正是 PDF 台存在的意义。
- **永远不能在 PDF 里改**：PDF 是终态，修复必须回到 docx。

**可扩展且值得做（可实现性高→低）：**

1. 空白页、图表跨页断裂、标题页底孤行、公式编号分页 → 把 PDF 台从 2 条扩到 6-8 条，体验立刻饱满。✅ 可行
2. 渲染评分/页数/问题数已有数据，前端已接。
3. 字符级高亮 → 二期，需 PDF 文本坐标，难，先不碰。

---

## 3. 最大真空：确认 → 我说怎么改 → 回填 → 定稿 闭环 ❌

**这是愿景里最核心、但当前完全不存在的东西。**

现状：`render-verify`（PDF 复核）是**只读终点**——只报告，报告完即结束。人在 PDF 台确认「这地方该这样改」，这个意见**没有任何通道流回 docx 生成最终稿**。

期望流程：

```
上传 → 自动修(structure) → PDF 复核台标出「机器改不了/要人确认」的点
   → 人逐项确认/给指令 → 工具回填 docx → 生成「最终稿」
```

缺的就是从 PDF 台往回的那条线。

**性质：功能缺口，不是技术难点。** 可实现性高，但需新设计：
- 确认项的数据结构
- 人的指令如何映射成 docx 操作（哪些能映射、哪些只能记为「待人工」）
- 「最终稿」作为独立阶段产物

---

## 4. 文件阶段梳理：能看懂，但「阶段感」弱 ⚠️

现在产物：`demo_格式修复_V01.docx`（输出）、`job_report.md`（报告）、`input`（原稿）。

能区分输入/输出/报告三档，但**缺乏清晰的生命周期阶段**。期望的「原稿 → 自动修复稿 → 人工确认后定稿」多阶段，目前只到「输出」一档。

**建议随第 3 点闭环一起做最自然。**

---

## 5. 报告：给人 / 给 AI 两种文案——现在都不够 ❌

当前 `job_report.md` 只有数字、没有清单：

```
# 任务审查报告
任务编号 / 类型 / 状态 / 时间
## 对应文件：输入 X，输出 Y
## 任务结论：未通过规则: 3，修复后提示: 2
```

它**不会**说「第几页摘要标题字号错、参考文献第 12 条缺类型标识、建议怎么改」。
而详细逐条发现（findings / evidence_items）**在审查结果里已存在，只是没被汇编进可下载报告**。

期望的两种文案，现在都没成型：

| 类型 | 用途 | 内容形态 |
|------|------|----------|
| 给 AI 看 | 整段贴进别的聊天 AI，处理本工具改不了的内容问题（语义、措辞） | 结构化逐条：规则 / 位置 / 现状 / 建议 |
| 给人看 | 学生直接读 | 口语化：哪有问题、已帮你改了什么、还剩什么要你定 |

**可实现性：高。** 原料（findings）已在，主要做两个 render 模板汇编现有数据。**性价比最高。**

---

## 整体判断与建议优先级

距离「彻底的一键修复工具」的差距，**不在修复引擎（够强），而在交付闭环**。

| 优先级 | 事项 | 性质 | 可实现性 | 价值 |
|--------|------|------|----------|------|
| 🥇 | 详细报告（给人 + 给 AI 两份） | 汇编已有数据 | 高，见效快 | 让工具「显得完整、立刻可用」 |
| 🥈 | PDF 确认 → 回填 → 定稿 闭环 | 新功能设计 | 中 | 愿景的灵魂 |
| 🥉 | PDF 渲染规则 2 条 → 6-8 条 | 扩检测 | 中 | 复核台饱满度 |
| 4️⃣ | 文件阶段生命周期 + 可读命名 | 随闭环做 | 高 | 文件梳理清晰 |

---

## 不在本评估范围

- 字符级 PDF 高亮（二期）
- 直接编辑 PDF
- 云账号 / 多用户同步
- 重新引入 Word 自动化作为主流程
