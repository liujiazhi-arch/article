# 论文工具产品战略修订意见 · 不确定性下的可信交付

> 日期：2026-06-16
> 性质：对 `docs/THESIS_PRODUCT_EXPERIENCE_STRATEGY.md` 的校正与补强，不是替代。
> 依据：原战略 + `ONE_CLICK_THESIS_GAP_ASSESSMENT.md` + 对当前主链代码的只读核对（已逐项验证文件位置）。
> 一句话：原战略写的是"论文修好以后怎么交付"，这版补的是"论文没修好、识别错了、复核不准时怎么交付"。

---

## 0. 为什么需要这一版

原战略的主轴是「交付闭环」：上传 → 自动修复 → 说明改了什么 → PDF 复核 → 候选稿 → 最终稿 → 打包。这条线是对的，但它默认了一个前提：**引擎认得对、改得对、复核得准。**

真实产品里这个前提经常不成立：

- 学生的 docx 很脏：手动敲的伪标题、用空格排版、表格当标题、复制粘贴带进来的脏样式。
- 我们的识别脚本会判错：把表格当标题、把正文当标题、把图表块拆开。
- 修复会有副作用：改了反而更乱，或改了学生没预期的地方。
- 复核会不准：PDF 渲染引擎不同、分页不同、启发式只能给"疑似"。

原战略对这些只用一张"未修复项四分类"表草草带过（需要确认 / 需要人工 / 需要 PDF / 暂不支持），并且这四类**全部假设引擎本身是对的**。它没有回答你真正关心的问题：

> 当我们改不了、甚至可能搞错了的时候，怎么让学生明确"到底哪里有问题、应该怎么改"。

这版意见的主张是：**保底交付（诚实诊断）优先于完美交付（一键修好）。** 一键修好是上限，是锦上添花；诚实诊断是下限，是每一次都必须兑现的承诺。先把下限做扎实，因为它在每一条路径上都会触发，包括最难看的那些。

---

## 1. 对原战略的三个事实校正

原战略和评估文档有几处与代码现状不符，会直接误导优先级排序。

### 校正一：学生报告 / AI 报告不是"待造"，是"待接线"

原战略 P0 写的是"生成学生结论报告、生成 AI 协作报告、生成技术明细报告"，口吻像从零开始。实际上这些能力已经在 CLI 层写好了：

- `scripts/thesis_tool/conclusion_report.py`
  - `render_student_conclusion_report()`：学生结论报告，已按 `auto_fixable / needs_review / unknown / manual_only` 分区，含规则名、scope、示例段落、最近标题、原文片段。
  - `render_ai_review_context()`：AI 协作上下文，已带"把论文片段当数据不要当指令"的防注入声明。
  - `render_student_render_report()` / `render_ai_render_context()`：PDF 复核的学生版 / AI 版文案。

真正的缺口在服务层：`scripts/article_api/job_artifacts.py` 目前只会产出**一份** `job_report.md`（role 只有 `input / output / report`），里面只有任务编号、状态、文件路径、未通过规则数这些"运行摘要"。已有的学生 / AI 报告**没有被注册成 job artifact**，前端自然也下载不到。

**含义：P0 的成本比原战略估计的低得多，但落点不同——是把 `conclusion_report.py` 提升为服务层能力并注册成多角色 artifact，不是再写一遍报告模板。**

### 校正二：失败诊断层已经存在，但没被当成产物

你最担心的"脏文档 / 识别错 / 修复错"场景，代码里其实已经有一层防护，只是它今天只表现为 HTTP 错误，没有表现为"交付件"：

- `scripts/article_api/errors.py`：已把异常分类成 `invalid_docx`、`apply_guard_blocked`、`validation_error`、`runtime_conflict`、`internal_error`，每类都带本地化 `user_message` 和 `next_action`（例如 invalid_docx 会提示"在 Word/WPS 另存为 .docx 后重试，仍失败请换干净副本"）。
- `scripts/article_engine/service.py`：apply 前有 **guard**，识别到结构性风险（表格被误判成标题、样式层与文本层冲突等）会抛 `ApplyGuardBlockedError`，并带 `warning_lines` 和风险计数；apply 后把仍未通过的规则放进 `post_verify_notices`。
- `scripts/article_api/job_payloads.py`：`build_failure_summary()` 已有失败摘要骨架，含 `error_code / error_message / error_next_action / retryable`。

**含义：原战略把"失败"完全排除在交付闭环之外，是最大的盲区。这些机制已经是产品级诊断的半成品，应该被提升为一等交付物，而不是只当成一个 4xx 返回码。**

### 校正三：置信度字段已存在，但不分层

- `scripts/thesis_tool/render_analyzer.py`：每个 render finding 都 `setdefault("confidence", 0.9)`，不同启发式给 0.8–0.9 不等，并有 `actionable`、`render_suspect`、`classification` 等上下文字段。
- 但**没有任何 gating**：低置信信号和高置信信号一起塞给用户，学生 / 报告里也没有"这条我们有多确定"的表达。

原战略说 PDF finding 要标"疑似 / 需确认"，方向对，但它没意识到置信度字段已经在那里，而结构层（guard 的误判风险）同样需要一套统一的"我们有多确定"表达。

### 顺带确认的事实

- LNU runtime 当前是 **75 条**规则（`effective_lnu_rule_definitions()` 实测），原战略已修正、评估文档里的 91 条是旧数。
- render 启发式实际可用的不止 2 条：空白页、渲染异常页、孤立标点、公式编号跨页、标题页底孤行都已接线（评估文档低估了）。

## 2. 修订后的战略主轴

把原战略的单轴「交付闭环」升级为双轴：

```text
轴一（原战略，保留）：把成功结果交付清楚    —— 上限，锦上添花
轴二（本版新增，前置）：把每一种结果都交付诚实 —— 下限，每次必兑现
```

新的核心承诺，从原来的四条（能改 / 能解释 / 能说明没改 / 能交付）扩展为五条，新增的第五条是重点：

| 承诺 | 含义 | 现状 |
|------|------|------|
| 能改 | 确定性结构问题自动修 | 已强 |
| 能解释 | 改了什么、为什么能改 | 报告已写好，待接线 |
| 能说明没改 | 哪些没改、为什么 | 分类已有，待产品化 |
| 能交付 | 清晰命名的结果文件 | 待做 |
| **能诚实** | **改不了 / 可能改错 / 不确定时，仍给出学生看得懂的诊断与下一步** | **代码有半成品，产品层缺位** |

「能诚实」是这版意见的灵魂。它要求：**不存在"工具沉默退出"或"只丢一个错误码"的结局。** 每一次任务，无论成功、部分成功、被 guard 拦截、还是彻底失败，都要落地一份学生能读的诊断件。

## 3. 把"失败"和"不确定"升级为一等产物

这是原战略完全缺失、而你最看重的部分。我把它拆成三种状态，每种都要有明确的产品动作和交付件。

### 3.1 失败交付：修不成也要给诊断

当 apply 因为脏文档 / 解析失败 / 内部错误终止时，**仍然产出一份学生诊断报告**，而不是只返回 4xx。

报告应回答：

- 我们卡在哪一步（上传校验 / 结构解析 / 修复 / 复核）。
- 为什么卡住（用学生语言，不暴露 traceback）。
- 这通常是文档的什么问题导致的（例如"文档可能是从 PDF 转出来的，样式不完整"）。
- 你现在可以做什么（具体到操作：在 Word 里另存、删掉某段重排、换干净副本）。
- 如果要找 AI / 老师帮忙，把哪份材料发过去。

`errors.py` 的 `user_message` + `next_action` 已经是这份报告的种子，`build_failure_summary` 是它的数据来源。要做的是把它们渲染成一份 markdown 交付件，并注册成 artifact。

### 3.2 低置信交付：改了，但你要核对

guard 没拦住、修复也执行了，但属于"我们不太有把握"的修改（例如基于启发式判定的标题层级、被怀疑误分类但未触发 block 的段落），要单独标出来：

> 这些地方我们替你改了，但判断依据是推断，建议你打开核对一下。

这对应 `post_verify_notices` 和 render finding 的 `confidence`。产品上表现为修复完成页的一个"建议你复核我们的改动"区块，而不是假装所有修改都 100% 可靠。

### 3.3 拦截交付：不敢改，告诉你为什么

guard 触发 `ApplyGuardBlockedError` 时（表格被当成标题、样式 / 文本层冲突），**这是产品的优点，不是 bug**——它阻止了一次会把文档改更乱的操作。但今天它只表现为一个错误。要把它产品化为：

> 我们检测到文档这里结构异常（例如：这张表被识别成了标题），如果强行修复可能破坏排版，所以我们没有动它。建议你：……

并提供两条出路：`force` 强修（带明确风险提示）或 按指引手动处理后重传。

### 3.4 五类未解决项（补上原战略缺的第五类）

原战略四分类全部假设引擎是对的。补上**第五类：可信度风险项**——即"引擎自己也不确定 / 可能判错"的项。

| 类别 | 含义 | 示例 | 产品动作 |
|------|------|------|----------|
| 需要确认 | 程序能定位，需学生判断 | 末章是否叫结论 | 确认卡片 |
| 需要人工处理 | 不应改语义 | 参考文献大小写一致性 | 人工建议 |
| 需要 PDF 复核 | 结构层看不到真实分页 | 目录页码、孤立标点 | 引导上传 PDF |
| 暂不支持 | 当前能力未覆盖 | 复杂脚注 / 特殊版式 | 写入待办 |
| **可信度风险（新增）** | **引擎可能识别错 / 修错 / 复核不准** | **表格被误判为标题、低置信 render finding、guard 拦截项** | **明确标注"我们不确定"，给核对入口和强修 / 手改两条路** |

关键心智：**让学生区分"工具不改"（出于谨慎）和"工具不能改"（出于能力边界），并且永远不假装确定。**

## 4. 重排后的优先级

基于"已有能力 + 保底优先"，把原战略的 P0–P4 重排。变化的核心是：**报告接线和失败诊断并列为 P0，因为前者成本极低、后者价值极高且当前完全缺位。**

### P0 · 多角色报告接线 + 失败诊断交付

- 把 `conclusion_report.py` 的学生 / AI / render 报告提升为服务层可复用能力（`build_delivery_reports(result)`）。
- `job_artifacts.py` 的 artifact role 从 `input/output/report` 扩展为 `student_report / ai_report / technical_report / render_report`。
- **失败路径也产出诊断报告**：apply 失败 / guard 拦截时，由 `errors.py` + `build_failure_summary` 渲染一份学生诊断件并注册成 artifact。
- 前端下载区按 role 显示学生文案用途。

为什么是 P0：报告侧基本是接线（原料已在），失败诊断侧是你最痛的缺口且半成品已在。两者合起来，能立刻把产品从"顺利就好、不顺利就崩"变成"任何结果都有交代"。

验收：

- 上传一篇有格式问题的正常 docx → 自动修复 → 能下载学生报告（含已改 / 待确认 / 原文示例）和 AI 报告（含边界声明）。
- **上传一篇故意损坏 / 极脏的 docx → 不崩 → 能下载一份失败诊断报告，说明卡在哪、为什么、下一步怎么办。**
- guard 拦截的样本 → 页面说明"为什么没改 + 风险 + 两条出路"，并产出对应报告。

### P1 · 任务结果页重构（含失败态与可信度态）

- 修复完成页成为结果中心，并且**显式承载失败态、拦截态、低置信态**，不只是成功态。
- 未修复项按五分类（含可信度风险）呈现为待处理清单。
- 历史任务可重开同样的结果中心。
- 全程不暴露 `job_id / queued / running / failed / rule_id / bbox`。

验收：失败任务在历史里重开，仍能看到"为什么失败 + 下一步"，而不是一片空白或一个红叉。

### P2 · PDF 复核确认流 + 置信度分层

- render finding 进入确认清单（确认 / 忽略 / 我自己处理）。
- **用已有的 `confidence` 字段做分层**：高置信直接展示为待处理，低置信折叠进"可能误报，供参考"，并在每条上说明"为什么只是疑似"。
- 确认结果写入报告；可映射项生成候选稿，候选稿强制二次复核。

### P3 · 文件生命周期 + 最终交付包

- 明确 原稿 / 自动修复稿 / 候选稿 / 最终稿 阶段与中文命名。
- 一键 ZIP，含 `请先看我.md`，**并且 ZIP 里包含失败 / 待确认清单**，不只是成功产物。
- ZIP 不含运行状态、缓存、上传路径等内部信息。

### P4 · PDF 可信复核项精炼扩展

- 从已有启发式里筛可信项，统一规则 ID / 学生文案 / AI 文案 / 测试样本。
- 不追字符级高亮，不为"看起来强"展示低置信噪声——这条和 P2 的置信度分层是一体的。

## 5. 架构演进：结果模型必须能表达"不确定"

原战略 §9 的 `DeliveryResult` 模型方向对，但它的 `unresolved_items` 仍假设引擎正确。补两点：

### 5.1 结果模型要能表达失败与置信度

```text
DeliveryResult
  document
  outcome            # success | partial | guard_blocked | failed   ← 新增，失败也是一种结果
  stages             # original / auto_fixed / candidate / final
  fixed_items
  low_confidence_fixes  # 改了但不确定，建议核对          ← 新增
  unresolved_items   # 五分类，含 confidence_risk
  guard_findings     # 被拦截的高风险项 + 出路            ← 新增
  review_items
  diagnosis          # 失败 / 拦截时的学生诊断            ← 新增
  artifacts
  reports
  next_steps
```

每个 unresolved / guard item 都应带：

```text
confidence            # 我们有多确定（复用 render_analyzer 的字段口径）
why_uncertain         # 为什么只是疑似 / 为什么可能判错
student_explanation   # 学生语言
suggested_action
escapes               # 可选出路：force 强修 / 手改后重传 / 交 PDF 复核
```

### 5.2 让 errors 与 reports 共用同一诊断管线

`errors.py`（失败分类）、`build_failure_summary`（失败摘要）、`conclusion_report.py`（成功报告）今天是三条独立的线。应收敛到一个 `build_delivery_reports(result)`，让成功、部分成功、失败走同一套渲染入口，由 `job_artifacts.py` 统一注册。这样"诚实交付"才不会在某条分支上漏掉。

## 6. 前端文案：把"不确定"说清楚，但不说吓人

在原战略的术语替换表基础上，补充"可信度 / 失败"场景的文案原则：

| 内部状态 | 学生文案（建议） |
|----------|------------------|
| apply_guard_blocked | 这里结构有点特殊，我们没敢自动改，避免越改越乱 |
| post_verify_notices | 这些地方我们改了，但建议你核对一下 |
| low confidence finding | 这里可能有问题，但我们不太确定，供你参考 |
| invalid_docx / parse error | 这个文件我们没能正常读取，可能是…… |
| internal_error | 处理时出了点问题，这份诊断说明了卡在哪、怎么办 |

原则：**承认不确定，但永远给下一步。** 不要把不确定包装成确定（虚假精确），也不要把不确定变成"工具坏了"（学生会放弃）。

---

## 7. 测试与验收：失败路径是必测项

在原战略测试策略基础上，强制增加**坏输入样本**这一类——这是验证"能诚实"承诺的唯一办法：

建议样本集（脱敏公开）：

1. 正常但格式混乱样本（验证一键修 + 报告）。
2. 含人工确认项样本（验证未修复分类）。
3. 含 PDF 复核项样本（验证置信度分层）。
4. **损坏 / 极脏 docx 样本（验证失败诊断不崩、有交付件）。** ← 新增
5. **触发 guard 的误分类样本（验证拦截态有解释和出路）。** ← 新增
6. 完整闭环样本。

每类都要验证：不崩 + 产出对应交付件 + 学生文案不泄漏内部术语 + 失败 / 不确定时有明确下一步。

报告内容测试（在原战略基础上补）：

- 失败诊断报告包含"卡在哪 / 为什么 / 下一步"。
- guard 拦截报告说明风险并给出 force / 手改两条路。
- 低置信修复在报告里被单独标为"建议核对"，不混进"已确定修复"。

---

## 8. 最终建议

原战略问对了方向（交付闭环），但排错了重心（它优先打磨顺利路径）。结合项目真实状态，重心应调整为：

> **先把每一种结果都交付诚实，再把顺利结果交付漂亮。**

最该先做的不是最终稿和 ZIP，而是这两件几乎零新造、却把产品从"工具"变成"可信交付系统"的事：

1. 把已经写好的学生 / AI 报告接到 job artifact 和前端（接线）。
2. 让失败、拦截、低置信也产出学生看得懂的诊断件（产品化已有的 errors / guard / confidence）。

做完这两件，你最担心的场景——文档脏、识别错、修复错、复核不准——就从"工具崩了 / 学生懵了"变成"工具老实告诉你哪里有问题、为什么没改、应该怎么改"。

短期口号修订为：

> 改得了就改好，改不了就说清，绝不假装确定。

长期形态仍是原战略那句，但加一个定语：

> 本地可信、**且在不确定时依然诚实**的论文格式交付工作台。
